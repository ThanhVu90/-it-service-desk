Branch `upgrade/p1-2-readiness`, based on merged `main` containing P0-1 + P0-2 + P1-1.

## Environment

Windows 11 x64, .NET SDK 10.0.403, EF Core 10.0.14. Live demo on a fresh seeded SQLite file; no personal data.

## Sequence

1. **Acceptance tests written first** (`95dc609`, no model change needed): 5 tests in `ReadinessTests` — 4 **red** (readiness endpoint missing → 404; no correlation id in bodies/headers; unhandled DB failure returned an empty 500), 1 leak-guard already green (404 bodies carry no paths/stacks). Baseline 49 stayed green.
2. **Implementation** (`fde264c`):
   - `HttpCorrelation.Run` is the outermost middleware: assigns `context.TraceIdentifier` from a validated caller header or a fresh 12-hex id, stamps `X-Correlation-ID` on the response via `OnStarting`, and converts `RuleException`/concurrency/`DbUpdateException`/antiforgery failures into Problem responses that embed `correlationId`, while anything unexpected is logged (`LogError` with id + method + path) and answered with a generic 500.
   - `/health/ready`: `CanConnectAsync` **and** applied migrations equal registered migrations on SQLite (Postgres stays experimental and probes reachability only, matching its EnsureCreated bootstrap). Any failure returns 503 via `HttpCorrelation.NotReady()`; the body names no files or connection data.
   - The security-header middleware (CSP, nosniff, referrer, api cache rules) was preserved as its own step.
3. **Full suite: 54/54 green.**

## Acceptance criteria mapping

| Guide criterion | Proof |
|---|---|
| `/health` liveness kept | `Liveness_stays_simple_and_readiness_reports_ready_when_the_schema_is_current` (200 `{"status":"ok"}` unchanged) |

## Live demo (guide: "readiness + a failed request with an id to find in the log")

Server console log, verbatim excerpt:

```
fail: ServiceDesk[0]
      Unhandled request failure 7e62c084d785 POST /api/login
      Microsoft.Data.Sqlite.SqliteException (0x80004005): SQLite Error 1: 'no such table: Users'.
```

- `GET /health` → 200 `{"status":"ok"}`
- `GET /health/ready` → 200 `{"status":"ready","database":"current"}` (schema current: 4 migrations)
- `POST /api/tickets` (empty title) → 400, header `X-Correlation-ID: 5b3a01e93361`, body `…"correlationId":"5b3a01e93361"`
- Store file deleted on disk; `POST /api/login` → 500 `application/problem+json` `{"type":"https://tools.ietf.org/html/rfc9110#section-15.6.1","title":"An unexpected server error occurred.","status":500,"correlationId":"7e62c084d785"}` — no stack, no path
- `GET /health/ready` after the break → **503** (fail closed), again without connection details
- Authenticated requests during the outage fail closed with 401 (`Session for user 1 rejected (database-unavailable)`), consistent with P0-2.

## Limits

- Readiness checks migration history, not row-level health; a database whose tables were hand-mutilated *in a way migration history cannot see* may still report ready.
- Correlation ids are not distributed-trace spans (no OpenTelemetry yet); ids are short and human-friendly.
- The 500 response does not include remediation text; operators find details in the log by id.
