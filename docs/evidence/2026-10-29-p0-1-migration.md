## Failure found and fixed during the run

First beta of the e2e check **failed on a real bug**: a database that already carried migration history was misclassified as legacy because the inspector skipped every `__`-prefixed name from `sqlite_master`, including `__EFMigrationsHistory` itself. The outcome was adoption refused with a safety snapshot (correct refusal behavior, wrong branch). Fixed by keeping EF-internal tables for history detection and excluding them only from the structural fingerprint; regression test `Database_with_migration_history_is_never_adopted_as_legacy_on_restart` was written first (red) and went green with the fix. This is why the restored-copy demo above is verified with the fixed build.

## Acceptance criteria from the upgrade guide

- Empty database starts: covered by `Fresh_empty_database_starts_through_controlled_migrations` and the hand run.
- Older-version database upgrades without ticket/assignment/audit loss: `Legacy_database_created_without_migrations_adopted_and_upgraded_without_losing_data` (users, ticket, asset, assignment, audit row preserved; a new ticket is created through `DeskService` on the upgraded file).
- Failed migrations do not leave the app "ready": initializer runs before the host starts, so a failing bootstrap throws and the process exits — `Corrupt_database_file_fails_startup_before_reporting_ready` plus the wrapped-upgrade-failure messages in code.
- Restore reads data and can create a new ticket: `Backup_restores_roundtrip_preserves_live_database_writes` plus the hand-run 401 on the restored file.
- Original snapshot is never overwritten silently: `Backup_never_overwrites_an_existing_destination` and CLI `--force` being explicit.
- Unrecognized schema refused with snapshot left behind: `Unrecognized_schema_is_refused_and_safety_backup_is_saved`.

## Limits of this run

- CI on Windows/Linux for this branch is not linked yet; the run link is recorded in `docs/VERIFICATION.md` after the branch push. Do not claim the CI badge until the run of this branch completes.
- The audit-table fingerprint comparison is strict: any extra table added manually to a pre-migration database makes adoption refuse (documented in README so it is not a surprise).
- `git revert` of the application build does not downgrade a database file; rollback stories all use snapshots.

## Demo note for interview/ticket context

Seven-minute flow for this item: fresh start (log line "Fresh SQLite database created"), stop, backup via CLI, show the snapshot file, restore to a new path, start the second instance on the restored copy, sign in with the restored users and create a ticket. Show the `Unknown schema` refusal by renaming a column with `ALTER TABLE` on a copy, then restore from the refused snapshot. All databases used in demos are copies; no personal data involved.
